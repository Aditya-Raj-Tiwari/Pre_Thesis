Verifying LLM-Generated Network Calculus Proofs

Findings, related work and a proposed verification framework · Bachelor thesis preparation, TUM · Aditya · 24 November 2026
Sources checked on 24 November 2026.
Summary.
  • Running code is not verification. Code that evaluates a delay bound checks only the arithmetic of one formula. A proof assistant (Lean 4, Coq/Rocq, Isabelle/HOL) accepts a proof only if every inference step follows from the stated assumptions; a small trusted kernel re-checks the result.
  • The remaining risk is the statement. The kernel guarantees that the proof proves this formal statement, not that the statement means what the textbook theorem means. For a benchmark, formal statements should be written once and reviewed by a human; the LLM writes only the proof.
  • Network calculus (NC) formalizations exist, mostly in Coq. ONERA's NCCoq is the only substantial library. In Lean, Meta's atlas-lean repository gained a small NC core on 21–22 November 2026 (curves, min-plus convolution, backlog/delay bounds, pay-bursts-only-once), built on the same Lean version as this project. Mathlib itself has no NC.
  • TSN shapers: I found no proof-assistant formalization of NC bounds for CBS, TAS, CQF or ATS. TSN shapers have been analysed with the UPPAAL model checker, so the gap is specifically "interactive proofs of NC shaper bounds".
  • Proposed design: four verification layers: (1) final answer vs. an NC tool, (2) symbolic/numeric step checks, (3) formal proof check of a human-reviewed subset, (4) LLM judges calibrated against layer 3. A working Lean 4 + Mathlib environment and a proof checker are already set up (Appendix A).

1. Why “run the Python code” is not verification

Code that computes T + b/R always prints a number, even if the derivation that led to T + b/R used the wrong service curve, ignored the FIFO assumption, or assumed r > R. It checks one formula on one input. It never checks whether that formula follows from the NC theorems and the problem's assumptions. A proof assistant does not evaluate the bound; it checks that the theorem “under these hypotheses, delay ≤ T + b/R” follows logically from definitions and earlier theorems.

2. How proof assistants verify

2.1 Terms

  • Proof assistant / interactive theorem prover: software in which definitions, theorem statements and proofs are written in a formal language and every step is checked mechanically. Relevant here: Lean 4 (with the Mathlib library), Coq (renamed the Rocq Prover with version 9.0, released 12 March 2025) and Isabelle/HOL.
  • Tactic: a command that transforms the current goal (e.g. intro, rw, linarith, nlinarith, simp).
  • Kernel: a small core that checks the final proof object, so bugs in tactics cannot produce an accepted false proof. Lean and Coq follow the de Bruijn criterion (proof objects checkable by a small independent checker). Isabelle follows the LCF approach, which Paulson describes as an alternative to the de Bruijn criterion with the same goal of a small trusted core; a Dagstuhl report describes Isabelle's logic as resting on “a very small kernel that needs to be trusted: a dozen axioms, that have been manually validated.”
  • Mathlib: Lean's community library. Per Wikipedia, as of May 2025 it contained over 210,000 theorems and 100,000 definitions.

2.2 Input and output, with a small NC-flavoured Lean example

Classical single-node result (Le Boudec & Thiran, Thms 1.4.1–1.4.2): a flow with token-bucket arrival curve α(t) = b + r·t for t > 0 (α(0) = 0) crossing a rate-latency server β(t) = R·[t − T]⁺ with R > 0 and r ≤ R has virtual delay at most T + b/R (the actual delay for a FIFO server) and backlog at most b + r·T. The full proof needs min-plus definitions (horizontal deviation involves both a sup and an inf). The example below is only a warm-up algebraic lemma, to show what input and output look like:

import Mathlib

theorem delay_ge_latency (b R T : ℝ) (hR : 0 < R) (hb : 0 ≤ b) :
    T ≤ T + b / R := by
  have h : 0 ≤ b / R := div_nonneg hb (le_of_lt hR)
  linarith

I ran all three outcomes with Lean 4.36.0 and Mathlib v4.36.0:

CaseLean output
Correct proofNo errors. #print axioms delay_ge_latency lists only [propext, Classical.choice, Quot.sound].
Wrong proof (delete the have line)Rejected: “linarith failed to find a contradiction”, with the remaining goal and hypotheses printed at that line. This step-level signal can be fed back to an LLM.
Incomplete proof (sorry)Compiles with the warning “declaration uses `sorry`”; #print axioms lists sorryAx. A checker must count this as a failure.
Smuggled axiomA file that declares axiom cheat : … and uses it compiles without any warning; only #print axioms reveals cheat. A checker must inspect axioms, not just warnings.

2.3 Placeholders differ between tools

  • Lean: sorry compiles with a warning and adds sorryAx.
  • Coq/Rocq: Admitted turns the goal into an axiom, by default without a warning; Print Assumptions reveals it.
  • Isabelle: sorry is accepted only interactively or in quick_and_dirty mode; a normal session build fails. oops abandons the proof and produces no theorem at all.

So a checker should verify three things: the named theorem exists, its statement is the fixed one, and its axiom dependencies are within policy. Not every published evaluator does all three (e.g. DeepSeek-Prover-V1.5's public verifier.py rejects errors and sorry but does not check for custom axioms).

2.4 The key limitation: statement faithfulness

The Weng et al. autoformalization survey (arXiv 2505.23486) notes that successful compilation “does not mean that autoformalization is completely correct.” Typical NC failure modes: missing hypotheses (stability r ≤ R, FIFO, non-decreasing curves, α(0) = 0); type traps (in Lean, (7 : ℕ) / 2 = 3 and x / 0 = 0, so a statement over ℕ or one allowing R = 0 can be provable but meaningless); vacuous statements (contradictory hypotheses); weakened conclusions.

Mitigations, strongest first: (1) human-written, human-reviewed formal statements, frozen per problem, with the whole statement file (imports, definitions, statement) and toolchain pinned; (2) back-translation to English and comparison; (3) automatic alignment checkers such as FormalAlign; (4) sanity tests: show the hypotheses are satisfiable (the statement is not vacuous), check that the statement is not closed by a trivial tactic, and check it against known counterexamples of weakened variants.

Numeric ground-truth tools:

  • Nancy (C#, MIT, github.com/rzippo/nancy): exact min-plus/max-plus operators on UPP piecewise-affine curves. The Python wrapper is a proof of concept covering part of the API through a separate nancy-http server.
  • Nancy-Playground (ECRTS 2026, github.com/rzippo/nancy-playground): console calculator with RTaW's playground syntax; matches RTaW on its own test suite, without a general compatibility guarantee.
  • NetworkCalculus.org DNC (formerly DiscoDNC; Java, LGPL-2.1, github.com/NetCal/DNC): TFA, SFA, PMOO, LUDB. Hand-computed test scenarios are in the separate DNC_func_tests submodule.
  • panco (Python, BSD-3, github.com/anne-bou/panco): FIFO LP analyses and a TSN module; calls lp_solve. Installed and tested in my setup.
  • Saihu (Python, MIT, EPFL): one interface over four back-ends: Linear TFA Solver, DNC, xTFA and panco.
  • RTaW-Pegase is commercial. RTaW's online min-plus playground is free and web-only for non-commercial academic use and its licence forbids benchmarking; the old URL currently returns HTTP 404.

Framing from TSN research: arXiv 2509.26368 (“Introducing Large Language Models into the Design Flow of Time-Sensitive Networking”) states that “as LLMs are not reliable for precise mathematical reasoning, external NC modules are required to compute accurate delay bounds.” That paper concerns numeric delay computation in a design workflow; whether LLMs can produce correct NC proofs is the related question this thesis would study.

6. Proposed verification framework

Benchmark (about 30–60 problems): Tier A, single node (token bucket + rate-latency: delay, backlog, output arrival curve); Tier B, composition (concatenation, pay bursts only once; FIFO / static-priority residual service); Tier C, TSN-flavoured (CBS or TAS service curves from published papers). Each problem has an informal statement, an IneqMath-style checkable task (bound estimation or relation prediction), a ground-truth answer from a tool or textbook, and for 15–25 Tier A/B problems a human-reviewed formal statement.

Model conditions: frontier and open LLMs, with and without retrieval over NC theory (Le Boudec & Thiran, Network Calculus, free online; Bouillard, Boyer & Le Corronc, Deterministic Network Calculus, ISTE/Wiley 2018). For the formal subset: (a) a general LLM writes the Lean proof; (b) a specialized prover (Goedel-Prover-V2, DeepSeek-Prover-V2-7B) receives the formal statement; (c) DSP-style informal proof → sketch → automation.

Layered verification:

  1. L1, final answer against Nancy / DNC / panco or a textbook formula, recorded as equal, looser, or below the reference (below needs a separate soundness check).
  2. L2, symbolic/numeric: SymPy/Z3 on extracted algebraic steps; numeric counterexample search on curves.
  3. L3, formal: the proof must compile against the frozen statement file and pinned toolchain; reject sorry, admitted goals and new axioms; record the failing step.
  4. L4, LLM judges: IneqMath-style step judges on the informal proof, with agreement measured against L3. A failed formal proof does not by itself show the informal proof was wrong, so disagreements need manual review.

Metrics: final-answer accuracy; step-wise judge accuracy; formal pass@k; the answer-vs-proof gap; an error taxonomy (wrong theorem, missing hypothesis such as r ≤ R, sup/inf mistakes, arithmetic); effect of retrieval; judge–kernel agreement.

Autoformalization, if evaluated, is a separate experiment.

7. Open questions for discussion

  1. Lean 4 (best LLM tooling; new atlas-lean NC core) or Coq/Rocq (NCCoq/Prosa reuse; weaker LLM tooling)? Any contact with the ONERA authors (Boyer, Roux)?
  2. Should the LLM produce formal proofs directly, informal proofs that are autoformalized (DSP/DTV style), or both as separate conditions?
  3. Who reviews the formal statements, and is a formal subset of about 15–25 problems acceptable?
  4. Which NC results define the benchmark: textbook single-node results only, or also TSN shapers (CBS, TAS, ATS)? Which papers are the source of truth?
  5. Which numeric tool is the reference: Nancy, DNC, panco, or a chair-internal tool?
  6. Is the IneqMath-style answer-vs-proof gap the main metric, and should LLM judges be validated against the formal checker?
  7. Compute budget and model access (API models vs. local open provers such as Goedel-Prover-V2-8B).

8. Caveats

  • “No proof-assistant formalization of TSN shaper bounds” and “no public Isabelle artifact for Mabille et al.” rest on targeted searches (24 Nov 2026), not an exhaustive survey.
  • The Lean NC code in atlas-lean is three days old; its scope, licence and stability need checking before relying on it.
  • Benchmark numbers are not comparable across papers: sampling budgets differ (pass@32 vs. pass@8192) and evaluation sets are revised (e.g. DeepSeek-Prover-V2's PutnamBench count fell from 49 to 47 after two misformulated problems were excluded).
  • Several cited works are preprints (e.g. DeepSeek-Prover-V2, the Weng et al. survey); ProsaBuddy (RTSS 2026), IneqMath and Ineq-Comp (NeurIPS 2025) are peer-reviewed.
  • A proof assistant verifies logic, not modelling: whether the NC model (curves, FIFO, shaper semantics) describes a real TSN switch remains an assumption outside any proof.
